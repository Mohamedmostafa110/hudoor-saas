## 1. Domain Entities & Core Invariants

### 1.1 Invariant: Tenant Isolation
- **Rule BR-TEN-001**: Every business entity (AcademicYear, Subject, Group, Student, Session, AttendanceRecord, AuditLog) must be permanently bound to a single `TeacherId`.
- **Rule BR-TEN-002**: No entity can be reassigned or transferred to another `TeacherId`.
- **Rule BR-TEN-003**: A query initiated by a teacher must never return, mutate, or reference records bearing a different `TeacherId`.

## 2. Academic Structure Rules

### 2.1 Academic Years & Terms
- **Rule BR-ACA-010**: A teacher may have multiple Academic Years, but **exactly one** Academic Year can be marked as `IsActive = true` at any given time.
- **Rule BR-ACA-011**: Historical Academic Years cannot be hard-deleted if they contain any associated sessions or attendance records. They can only be marked as `IsArchived = true`.
- **Rule BR-ACA-012**: New sessions can only be created within an Academic Year where `IsActive = true` and `IsArchived = false`.

### 2.2 Subjects & Groups
- **Rule BR-ACA-020**: A Subject represents a course or curriculum level (e.g., "Arabic - First Secondary").
- **Rule BR-ACA-021**: A Group represents a cohort of students meeting together for a Subject in a specific Academic Year (e.g., "Group 1 - Saturday 10:00 AM").
- **Rule BR-ACA-022**: A Group must be associated with exactly one Subject and one Academic Year.
- **Rule BR-ACA-023**: Deleting a Group is only permitted if **zero** sessions have been conducted for it. If sessions exist, the Group can only be set to `IsArchived = true`.

### 2.3 Student Registration & Group Membership
- **Rule BR-STU-030**: A Student is registered under a Teacher and can be enrolled in one or more Groups within the active Academic Year.
- **Rule BR-STU-031**: **Group Transfer Integrity**:
  - When a student is transferred from Group A to Group B:
    - The student's membership in Group A is closed (`LeftDate = UtcNow`).
    - A new membership in Group B is created (`JoinedDate = UtcNow`).
    - **Crucial Rule**: Historical attendance records from Group A sessions remain permanently attached to Group A sessions and to the student. They are never deleted or retroactively reassigned to Group B.
- **Rule BR-STU-032**: A student cannot have duplicate active enrollments in the same Group at the same time.

## 3. Student Identity, Code Generation & Password Management

### 3.1 Code Structure & Format
- **Rule BR-COD-040**: Every student is assigned a `StudentCode`.
- **Rule BR-COD-041**: **Uniqueness Scope (Single Login Screen Requirement)**:
  - *Confirmed Requirement*: Students log in through a single unified portal by entering `StudentCode` and `Password`, without picking or identifying their teacher first.
  - *Architectural Invariant*: To guarantee deterministic lookup on a single login screen, `StudentCode` must be **globally unique across the entire platform** (enforced via a SQL Server unique index).
  - *Proposed Format (Pending Approval)*: A 6-to-8 character alphanumeric string excluding ambiguous characters (`0`, `O`, `1`, `I`, `L`). Example format: `HD-8492` or base32 `W7M-49D`.
- **Rule BR-COD-042**: The Student Code can be regenerated by the teacher if compromised. Regenerating the code increments the student's `TokenVersion`, invalidating all active sessions.

### 3.2 Student Password & Teacher Reset Rules
- **Rule BR-PWD-045**: **Student Code + Password Authentication**:
  - Students authenticate using their unique `StudentCode` and `Password`.
  - Self-registration is strictly disallowed; accounts are created exclusively by the teacher.
- **Rule BR-PWD-046**: **Absolute Plaintext Privacy**:
  - Passwords must always be hashed with salt (Argon2id or PBKDF2 with HMAC-SHA512).
  - Under no circumstances can a teacher, PlatformAdmin, or database operator inspect an existing active student password. The system exposes no API or interface to read password values.
- **Rule BR-PWD-047**: **Simplified Teacher-Driven Reset**:
  - If a student forgets their password, the teacher can trigger "Reset Password" from the student's profile.
  - The system dynamically generates an easy-to-read temporary password:
    - **Characters**: Letters and numbers only (no symbols like `!@#$%^&*`).
    - **Format Examples**: `Falcon482`, `Cedar735`, `Swift924` (derived from neutral words).
    - **Readability**: Excludes confusing characters (`0`, `O`, `1`, `I`, `l`).
    - **Generation**: Generated using a Cryptographically Secure Pseudorandom Number Generator (CSPRNG) selecting from a static list of neutral English/transliterated words plus digits. It is **strictly prohibited** from utilizing the student's name, phone number, birth date, or any personal data.
  - The plain temporary password is shown to the teacher on screen once to share verbally or in writing with the student, and is immediately stored as a cryptographic hash.
  - Strictly avoids OTPs, SMS gateways, email verification, or complex third-party workflows.
- **Rule BR-PWD-048**: **Enforced Password Replacement**:
  - An account provisioned with a temporary password (initial registration or teacher reset) has `MustChangePassword = true`.
  - The student can authenticate using the temporary password, but is forced to set their own new password before accessing any attendance records or QR scanner tools.
- **Rule BR-PWD-049**: **Atomic Session Invalidation & Expiration**:
  - **Atomic Token Invalidation via Database TokenVersion**: Executing a password reset or password change updates the password hash and increments `TokenVersion` atomically within a single database transaction. Every subsequent student request validates the JWT claim against the database value; prior tokens become invalid on their immediate next request with zero reliance on stale caches or external Redis infrastructure.
  - **Temporary Expiration (Proposed Default)**: Unredeemed temporary passwords expire automatically after a configurable period (**Proposed Default: 7 days**, pending explicit client approval).
- **Rule BR-PWD-050**: **Audit Logging**:
  - Every teacher-initiated password reset is written to `PasswordResetAuditLogs` with: `StudentId`, `TeacherId`, `TimestampUtc`, and `ClientIpAddress`.
- **Rule BR-PWD-051**: **Student Voluntary Password Change**:
  - Students may change their password whenever they wish by providing their existing password and a valid new password. Successful password changes also increment `TokenVersion` and issue a new JWT.

## 4. Attendance Session Rules

### 4.1 Session Creation & Scheduling
- **Rule BR-SES-050**: **Fluid On-Demand Scheduling**:
  - Sessions are created dynamically by the teacher whenever needed. There is no requirement for recurring calendar scheduling.
  - A session can be created for:
    - A single Group.
    - Multiple combined Groups (e.g., joint revision lecture).
- **Rule BR-SES-051**: **Session State Machine**:
  ```
  [ Draft ] ──▶ [ Active (Open for Attendance) ] ──▶ [ Closed (Ended) ] ──▶ [ Archived ]
  ```
  - `Draft`: Session configured but not open for attendance.
  - `Active`: Live session. Attendance can be recorded via QR scanning or manual checklist.
  - `Closed`: Session concluded. Self-service QR scanning is disabled. Further changes require teacher override.
  - `Archived`: Finalized historical session.

## 5. Attendance Recording & Auditability

### 5.1 Status Definitions
- **Rule BR-ATT-060**: Every enrolled student in a session must resolve to exactly one of the following statuses:
  1. `Present`: Student attended the session.
  2. `Absent`: Student was expected but did not attend.
  3. `Late`: Student attended after the grace window (optional `MinutesLate` integer).
  4. `Excused`: Student did not attend, but has an authorized excuse (optional `ExcuseReason` text).
- **Rule BR-ATT-061**: By default, when a session is closed, any enrolled student who did not check in via QR or manual check is automatically marked as `Absent`.

### 5.2 Dynamic QR Code Attendance Flow
- **Rule BR-ATT-070**: **Dynamic Token Rotation**:
  - The teacher's screen renders a QR code containing an encrypted/signed token: `HMAC_SHA256(SessionId + TimestampUtc + Salt, SecretKey)`.
  - The token rotates dynamically every **20 seconds**.
  - Expired tokens older than a small tolerance window (e.g., 40 seconds to account for clock skew) are rejected.
  - This prevents students from photographing the QR code and transmitting it to absent peers outside the classroom.
- **Rule BR-ATT-071**: **Student Verification Sequence**:
  1. Student logs into the student PWA using `StudentCode` + `Password`.
  2. Student scans the rotating QR code using the in-app camera scanner.
  3. Backend confirms:
     - `Session.Status == Active`
     - `Student.IsActive == true`
     - Student is enrolled in one of the session’s target groups.
     - QR token signature is valid and within the active time window.
     - Student has **not already checked in** for this session.
  4. If all validations pass, backend records `Status = Present`, `Method = QRCode`, `RecordedAt = UtcNow`.
- **Rule BR-ATT-072**: **Duplicate Check-In Prevention**:
  - A database unique constraint on `(SessionId, StudentId)` guarantees that a student cannot have multiple attendance rows for the same session.
  - Subsequent scan attempts for the same session return `ALREADY_CHECKED_IN` with the original timestamp.

### 5.3 Post-Session Editing & Audit Trail
- **Rule BR-AUD-080**: A teacher can modify any attendance record at any time after the session has closed.
- **Rule BR-AUD-081**: Every modification must generate an immutable `AttendanceAuditLog` record containing:
  - `AttendanceRecordId`
  - `OldStatus`
  - `NewStatus`
  - `ChangedByTeacherId`
  - `TimestampUtc`
  - `Reason` (mandatory if changing between Absent and Present after 24 hours).
- **Rule BR-AUD-082**: Audit logs are append-only. No user, including `PlatformAdmin` or `Teacher`, possesses permission to delete or alter audit log entries.

## 6. Academic Year Rollover & Progression Workflow

### 6.1 Rollover Invariants & Rules
- **Rule BR-ROL-090**: **Absolute Zero Data Loss**:
  - Advancing an academic year must **never** execute `DELETE` or `CASCADE DELETE` on historical tables (`Sessions`, `AttendanceRecords`, `HistoricalEnrollments`).
- **Rule BR-ROL-091**: **Progression Actions**:
  When transitioning from Academic Year $Y_1$ to $Y_2$, each student in $Y_1$ is categorized into one of three states:
  1. **Promote (ترقية)**:
     - Student advances to the next grade level (e.g., Grade 10 $\rightarrow$ Grade 11).
     - Student is enrolled into a new group in $Y_2$ or left in the unassigned pool for $Y_2$.
     - Past attendance in $Y_1$ remains linked to $Y_1$.
  2. **Repeat (إعادة السنة)**:
     - Student remains at their existing grade level in $Y_2$.
     - Student is enrolled into a $Y_2$ group for that same level.
     - Past attendance in $Y_1$ remains linked to $Y_1$.
  3. **Depart / Inactive (مغادرة / أرشفة)**:
     - Student has graduated or discontinued studies with the teacher.
     - Student is marked `IsActive = false` for $Y_2$.
     - Profile and all past historical attendance remain intact and accessible for historical inquiries.
- **Rule BR-ROL-092**: Once $Y_2$ is activated, $Y_1$ is automatically set to `IsArchived = true`. Existing sessions in $Y_1$ become read-only, preventing retroactive accidental session creation in an archived year.
